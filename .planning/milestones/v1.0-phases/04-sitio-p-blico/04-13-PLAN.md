<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Server Action (submitContact) | Network and deployment skew can make the call reject on the client |
| thrown value → visitor UI | error.tsx receives whatever was thrown (client values as-is; server errors as digest in production) |
| admin-controlled settings.email → public mailto href | Value written only by the authenticated admin, rendered on public pages |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-31 | Information disclosure | src/app/[locale]/error.tsx | mitigate | The component never renders or logs `error` (no message, digest or stack); error.test.tsx asserts a thrown "secret db detail" message and digest are absent from the DOM |
| T-04-32 | Denial of service | contact-form.tsx onSubmit | mitigate | try/catch around `await submitContact` maps any rejection to the 'unavailable' alert with mailto and keeps values, so redeploy skew or a network failure no longer replaces the page with Next's generic error |
| T-04-33 | Information disclosure | contact-form.tsx catch block | mitigate | `catch {}` binds nothing; the alert text is the fixed localized 'unavailable' string, never the thrown message (test asserts "Failed to find Server Action" is not in the DOM) |
| T-04-34 | Tampering | mailto href from settings.email in error.tsx | accept | Same exposure as the existing contact page mailto; the value is written only by the authenticated admin (requireSession in site-settings actions) and is not user-supplied at the public boundary |
| T-04-35 | Denial of service | retry() loop | accept | retry is user-initiated per click; no automatic retry loop is added |
</threat_model>
