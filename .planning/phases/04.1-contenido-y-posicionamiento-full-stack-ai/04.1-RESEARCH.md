## Summary

This phase is content work plus one risky operation: overwriting published production rows. The code already has everything the load needs. It has pure, script-safe Zod schemas per entity (`src/features/*/validation.ts`, no `server-only`), an unguarded DB factory (`src/db/client.ts`), a production guard (`src/lib/seed-guard.ts` with the `ep-billowing-union` main prefix), a snapshot and restore pair (`exportContent` / `seed --from-content`), a strict Tiptap allowlist (`src/lib/rich-text-schema.ts`), and a project content contract with em-dash and digit-parity checks (`docs/content/*.md` + `content-schema.ts`). The Server Actions themselves cannot be imported from a `tsx` script, because `@/db` and `@/lib/dal` import `server-only` and `next/headers`. "Reuse core write functions" therefore means extracting each action's private `toColumns` into a pure module that both the action and the script import.

**Invalidation decision (D-14):** use a **production redeploy after the main load**. The bundled Next 16.4 docs state that neither `'use cache'` nor `'use cache: remote'` carries over to a new deploy, because the cache key includes the build ID [CITED: node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-cache.md L261]. Vercel also scopes ISR output per deployment. A deploy re-prerenders every page, including the new Prendo and bot slugs, from Neon main. There is a further reason to deploy. Production (`origin/main`, last deploy 7 days ago, commit `ad0c575` of 2026-11-18) still runs **Phase 3 code**, and local `main` is 120 commits ahead. The Phase 4 public site is not in production yet, so content loaded into main can only be judged on a build of current code. A revalidation route is rejected: it adds a route and a secret, which needs approval, for a one-off. Publishing through the admin with no-op publishes is the documented fallback if Teo does not want production deployed before Phase 5.

**CV:** `generateCv` is a Server Action. It needs an admin session and `BLOB_READ_WRITE_TOKEN`, which exists in Vercel Production since 03-13 and is likely absent locally (e2e skipped 3 Blob specs). Run it from the production admin after the deploy. `buildCvData` reads the uncached `*Core` functions, so it always sees the DB. It calls `updateTag(tags.resume)` itself.

**Primary recommendation:** Draft everything in one review doc whose baseline is a fresh snapshot of **main** (not the stale local `content/`). After Teo approves, put the approved texts into their seedable sources (`docs/copy.md`, `docs/content/<slug>.md`, and one typed module for education, skills, SEO and structure). Then run `scripts/load-content.ts --target dev`, verify on a local `pnpm build && pnpm start`, and have Teo run `--target main --apply --allow-production` after a main snapshot. Deploy Production, generate the CV in the admin, and verify.

| Option | Works from a script? | Evidence | Verdict |

A `tsx` process has no incremental cache | "`revalidateTag` can be called in Server Functions and Route Handlers." `'max'` serves stale content once (SWR). `{ expire: 0 }` is for webhooks [CITED: revalidateTag.md] | Would need a new `/api/revalidate` route plus a secret. **Rejected:** new route and new env var need approval, for a one-off |
| **New production deployment** | Yes (`vercel --prod` or push `main`; `vercel.json` buildCommand = `pnpm db:migrate && pnpm build`) | "Neither caching directive carries over to a new deploy, because the cache key includes the build (or `deploymentId`) ID." ### Pattern 1: Extract pure column mappers (the "core write function" reuse)
**What:** Move each action's private `toColumns` (projects, experience, education, skills, site-settings) into `src/features/<e>/columns.ts`, with no `server-only`, `next/*` or `@/db` imports. `actions.ts` imports it. The script imports the same one.
**Why:** `actions.ts` files are `"use server"` and import `@/db` (`import "server-only"`), `@/lib/dal` (`next/headers`) and `next/cache`. They cannot run under `tsx` [VERIFIED: src/db/index.ts, src/lib/dal.ts]. This refactor changes nothing visible, so it is inside autonomy. Existing `actions.test.ts` files guard it.
**Script owns:** natural-key lookup, insert-or-update, relation replacement, `draft: null`, and the guard. The admin owns sessions and tags.

### Pattern 2: Explicit target + dry-run by default
- `--target dev|main` is required. Compare it to `describeDbTarget(DATABASE_URL)`: main ⇔ host starts with `PRODUCTION_DB_ENDPOINT_PREFIX` (`ep-billowing-union`). Abort on mismatch in either direction. On top of that, `--allow-production` is required for main (reuse `assertNotProduction`).
- Without `--apply`, print a per-entity, per-field diff (old → new, truncated to about 80 chars) plus counts, and exit 0. Never print the URL. Print only `describeDbTarget`.
- `--apply` runs one `db.batch` per entity group, so each group is atomic. Neon HTTP has no interactive transactions.
- Re-running with the same input gives an empty diff. That is the idempotency check.

### Pattern 3: Natural keys (no unique index exists for most tables)
| Table | Key | On match | On miss |
|---|---|---|---|
| site_settings | `id = SITE_SETTINGS_ID` | update only the approved text columns | error (row always exists) |
| projects | `slug` (unique) | update text fields, `order`, `featured`, `visible`; **keep `media`, `cover_image`**; set `status='published'` when the payload passes `projectPublishSchema` and Teo approved publishing; `draft=null` | insert |
| skills | `name` (unique) | update category, years, featured, order | insert published |
| experiences | `company` + `type` + `start_date` | update | insert |
| education | `institution` + `program_en` | update | insert |
| project_skills / experience_projects / experience_skills | parent id | delete + insert inside the same batch as the parent | — |

### Pattern 4: Pending `draft` on published rows
If a target row has `draft IS NOT NULL` (unsaved admin edits), dry-run must **list it**. `--apply` overwrites columns and sets `draft = null`. The snapshot keeps the old draft. This also avoids CR-01 (stale relation ids inside drafts block publish).

### Anti-Patterns to Avoid
- **Writing from the stale local `content/` export.** It is from 2026-11-16, most likely dev (it contains `e2e-stale-probe`, `now_*` null and empty Sofka bullets). Production got Sofka bullets, Now and ManuJ via the admin on 2026-11-21. The baseline is a fresh `export:content` of the target.
- **Writing `docs/content` `media`/`coverImage` (`material/...` paths) into the DB.** Blob URLs uploaded in production would be lost. The seed-map already omits them. Keep it that way.
- **Adding `captionEn/Es` or `capturedAt` to media while production runs Phase 3 code.** Production's `projectDraftSchema` is the old `strictObject` and would reject those keys in the admin until deploy [VERIFIED: git diff origin/main..main -- src/features/projects/validation.ts].
- **Importing `actions.ts` from the script** (server-only crash), or calling `revalidateTag` from a script (no effect).
- **Running `pnpm seed --force` as the loader.** It only inserts missing rows and never updates [VERIFIED: scripts/seed.ts header].

## Common Pitfalls

### Pitfall 1: The baseline is not production
**What goes wrong:** the review doc and the diff are built from local `content/*.json` (16 Nov, dev). Teo approves "changes" against text that is not live, and the load wipes his 03-13 Sofka bullets and Now.
**How to avoid:** the first task is a main snapshot (Teo runs `DATABASE_URL='<main>' CONTENT_EXPORT_DIR=content/snapshot-main-2026-11-xx pnpm export:content`, which stays under gitignored `/content/`). The review doc's "Actual" column comes from it.
**Warning signs:** Sofka bullets are empty in the baseline.

### Pitfall 2: Overwriting Blob media or covers
**How to avoid:** the loader's update allowlist excludes `media` and `cover_image`. A unit test asserts that a payload carrying them is rejected or ignored.

### Pitfall 3: The label has no field
**What goes wrong:** the planner plans a "label" column or a UI badge (data-model change and new UI, both need approval).
**How to avoid:** the label lives in the headline sentence, `seo_title_*` and the freelance `role_*`. Flag this to Teo in the review doc (the CV header and JSON Resume `label` both print the full headline).

### Pitfall 4: human_verify_mode = end-of-phase
`.planning/config.json` sets `"human_verify_mode": "end-of-phase"`. The content approval must **block** the load, so it cannot be deferred to the end. The planner should model it as a blocking checkpoint (decision or human-verify) before the load wave, and the main run as a `checkpoint:human-action` that Teo executes.

### Pitfall 5: Prohibited content slipping through
An em-dash (U+2014), a price ("COP", "$", "USD", "millones", "M"), infra identifiers (`fly.dev`, `supabase.co`, `.vercel.app` of Prendo, `iad`), markers (`TODO`, `[Teo escribe]`, `lorem`), "frontend" in the freelance role or headline, Prendo copy without "en desarrollo"/"in development", the Prendo AI feature in present tense.
**How to avoid:** a pure `content-lint.ts` with tests, run by the loader's dry-run (fail = exit 1) and by `check-phase-4-1.ts` on main. Its output is a check, not proof. Teo's review is the real gate.

### Pitfall 6: Translation adds or changes numbers
**How to avoid:** reuse the digit-parity rule from `docs/content` (`2,5` = `2.5`). Apply it to every en/es pair in the loader, not only projects.

### Pitfall 7: CV overflows two pages
Five extra education rows plus longer bullets plus more featured projects can push the CV past two pages. `check-cv-pdf.ts` fails above 2.
**How to avoid:** keep 3–4 bullets per experience, feature 3–4 projects, and put course hours in `status_*`. Hiding courses from the CV would need code, so fit them instead.

### Pitfall 8: Hero headline length
The hero splits the headline into words with a stagger capped at 200 ms and is the LCP element. A long sentence wraps to many lines on 390 px.
**How to avoid:** keep it to one sentence of about 12–20 words, then capture at 390, 768 and 1440 px (CLAUDE.md rule for public views) and re-run Lighthouse on `/` and `/es`.

### Pitfall 9: Restore side effect
`pnpm seed --from-content` replaces all 9 content tables and **re-hashes the admin** with local `ADMIN_EMAIL`/`ADMIN_PASSWORD`. Document this in the rollback note.

### Pitfall 10: docs/copy.md parser coupling
`readAbout` needs `## About` with `EN:`/`ES:` blockquotes. `readFreelanceBullets` needs a `### Freelance` heading with `- EN:` / `  ES:` pairs. Renaming the heading (for example to "Freelance · AI Full Stack Developer") still matches `^### Freelance\b`. Removing it breaks `pnpm seed`. Keep the structure, and add `readHeadline`/`readNow` parsers if the loader reads those from copy.md.

```ts
// Source: src/lib/rich-text-schema.ts (allowlist) — verified in repo
import { richTextDocSchema } from "@/lib/rich-text-schema";

type Inline = { text: string; href?: string; bold?: boolean };

export function paragraphsToDoc(paragraphs: Inline[][]) {
  const doc = {
    type: "doc" as const,
    content: paragraphs.map((parts) => ({
      type: "paragraph" as const,
      content: parts.map((p) => ({
        type: "text" as const,
        text: p.text,
        ...(p.href || p.bold
          ? {
              marks: [
                ...(p.bold ? [{ type: "bold" as const }] : []),
                ...(p.href ? [{ type: "link" as const, attrs: { href: p.href } }] : []), // https:// or mailto: only
              ],
            }
          : {}),
      })),
    })),
  };
  return richTextDocSchema.parse(doc); // throws on any disallowed node/mark/href
}
// Allowed nodes: doc, paragraph, text, heading (attrs.level 3 only), bulletList, orderedList,
// listItem, blockquote, code, hardBreak. Marks: bold, italic, code, link{href, target?, rel?, class?}.
// A list: { type: "bulletList", content: [{ type: "listItem", content: [{ type: "paragraph", content: [...] }] }] }
```
