# Phase 04.1: Code Review Report

**Reviewed:** 2026-11-25
**Depth:** standard
**Files Reviewed:** 25
**Status:** issues_found

## Summary

Reviewed the content loader (`scripts/load-content.ts` plus `src/lib/content-load/*`), the phase gate script, the `toColumns` → `*Columns` refactor in five features, the copy.md readers, the content lint, and the per-skill segment change in the case header and entry list.

Results on the focus areas:

- **Production safety:** dry-run is the default, `--apply` must match exactly, and `--target=main` requires both the `ep-billowing-union` host and `--allow-production`. The weak points: `dev` only means "not main" (WR-03), dry-runs against main also need `--allow-production` (WR-04), and writes are atomic per group but not across groups (WR-02).
- **Idempotency:** a rerun with unchanged sources produces zero statements. `canonical()` sorts jsonb keys, `undefined` and `null` compare equal, and the column mappers normalise `""` to `null` the same way on both sides. The weak point is natural-key drift: an admin edit to a key field causes a duplicate insert on the next run (WR-05).
- **Diff and plan:** rename and retire planning is correct and fails closed when both slugs exist. The settings group clears the draft without reporting it (CR-01), unlike every other group.
- **Secrets:** nothing prints the URL. `describeDbTarget` logs only the host, `requireEnv` names the variable but not its value, and `formatChange` prints content only. No issue found.
- **React keys `stack-${skill}`:** cannot collide. `skills.name` has a unique index (`skills_name_idx`), and `project_skills` has a primary key on `(project_id, skill_id)`. So for one project, `projectStacksQuery` returns each name at most once, including in draft mode. The `stack-` prefix also keeps these keys apart from the fixed segment keys (`internal`, `live`, period). No issue found.
- **Refactor:** the five `columns.ts` files are faithful moves of the old `toColumns`. That includes skills' `blank()` trimming, which differs from the other features on purpose.

## Critical Issues

### CR-01: Settings group silently discards a pending admin draft (data loss not shown in dry-run)

**File:** `scripts/load-content.ts:698-708`
**Issue:** Every other group calls `noteDraft()`, which prints `! ...has a pending draft (will be cleared)` and counts it. The settings group skips that call but still writes `draft: null` whenever any loaded field differs. `site_settings.draft` holds the whole settings payload: name, email, availability, calendar URL, social links. Any of those fields saved but not published in the admin is destroyed on `--apply`, and the dry-run never mentions it. The reverse case is also wrong. If nothing differs (`found.length === 0`) but a draft exists, the draft is kept. That draft predates the load and still holds the old headline, bio and now. The next "Publish" in the admin would revert the loaded copy.
**Fix:**
```ts
const cleared = noteDraft(group, "site", row);
const found = diffFields("settings", "site", row, columns, fields);
noteChanges(group, found);
if (found.length > 0 || cleared) {
  const picked = Object.fromEntries(fields.map((f) => [f, columns[f]]));
  group.statements.push(
    db.update(siteSettings).set({ ...picked, draft: null })
      .where(eq(siteSettings.id, SITE_SETTINGS_ID)),
  );
}
```
A better option: refuse to `--apply` while any target row has a draft, unless `--discard-drafts` is passed.

## Warnings

### WR-01: Loader never invalidates cache tags or runs exportContent

**File:** `scripts/load-content.ts:723-731`
**Issue:** Public queries use `'use cache'` + `cacheLife('max')`. The CLAUDE.md mutation contract is `updateTag` → `exportContent()`. The loader writes straight to the database and does neither. After a `--target=main --apply`, production keeps serving the old content until a redeploy. That happened to be the next step in 04.1-12, but nothing enforces it, and the content export (`pnpm export:content`) drifts from the database.
**Fix:** After `applied`, print a mandatory next step and exit non-zero until it is acknowledged. Better: call an authenticated revalidation endpoint that does `revalidateTag(tag, 'max')` for `tags.settings/skills/projects/experience/education`, then run `exportContent()`.

### WR-02: Apply is atomic per group, not per run; a mid-run failure leaves a partial load

**File:** `scripts/load-content.ts:724-727`
**Issue:** Groups are applied in separate `db.batch` calls, in this order: retire → skills → projects → experiences → education → settings. Retire deletes rows. If a later batch fails (unique violation, a duplicate name in `positioning.skills`, a network error), the earlier groups stay committed. The script then prints only `error.message`, with no record of which groups were applied. Planning resolves ids up front, so all statements could go in one batch.
**Fix:** Run a single `db.batch(groups.flatMap((g) => g.statements))`. neon-http batches run as one transaction. If the batch size limit is a concern, at least log `applied: <entity>` after each group so a partial run is visible.

### WR-03: `--target=dev` is a negative check; any non-main database counts as dev

**File:** `src/lib/content-load/target.ts:58-61`, `src/lib/seed-guard.ts`
**Issue:** `isMain` is `described.startsWith("ep-billowing-union")`. Anything else passes as `dev`, with no `--allow-production` needed. Some ways this goes wrong:
- The production endpoint changes (a Neon restore or branch reset creates a new endpoint id).
- A non-Neon or different-project production URL ends up in `DATABASE_URL`.

In both cases the script writes with only `--target=dev --apply`. The `VERCEL_ENV` fallback does not help locally.
**Fix:** Also pin the dev endpoint (a host, not a secret), for example `DEV_DB_ENDPOINT_PREFIX`. Have `assertTargetMatches` require a positive match for each target, and reject unknown hosts.

### WR-04: Dry-run against main requires `--allow-production`, which turns the flag into a habit

**File:** `scripts/load-content.ts:227-231`
**Issue:** `assertNotProduction` runs before the `args.apply` check. A read-only dry-run against main therefore needs `--allow-production` too, and the documented main flow is to pass it on every run. Once the flag appears on every main invocation, `--apply` is the only real safeguard. The two-key design ends up with one effective key.
**Fix:** Call `assertNotProduction` only when `args.apply` is true. Then `--allow-production` appears only on the run that writes.

### WR-05: Natural keys include editable fields; an admin edit causes a duplicate insert

**File:** `src/lib/content-load/plan.ts:69-83`, `scripts/load-content.ts:268-307, 447-469, 587-626`
**Issue:**
- Education is keyed by `institution|programEn`.
- Experiences are keyed by `company|type|startDate`.
- Skills are keyed by the case-sensitive `name`.

If Teo fixes a program title, a start date, or a skill's casing in the admin, the next load finds no match and inserts a second published row. For experiences, the old row is no longer "managed", so the loader never touches it again. The `Css` comment in `positioning.ts` already works around this. Nothing in the dry-run flags the new row as a probable duplicate.
**Fix:** When a `+ new` row matches an existing one on a weaker key (same institution, same company and type, case-insensitive skill name), print a `! possible duplicate of <id>` line and refuse `--apply` without an explicit override. Or store a stable `source_key` per entry.

### WR-06: Project draft clearing destroys unpublished case-study edits

**File:** `scripts/load-content.ts:361-379, 408, 424`
**Issue:** The case study is authored only in the admin editor. The payload takes `caseStudyEn/Es` from `projectFormValues(row)`, which is the published columns. The update then sets `draft: null`. Any case study saved as a draft but not published is lost, and the dry-run says only "will be cleared". The phase's Core Value is the case studies, and this is the one field the loader has no source for.
**Fix:** If `row.draft` contains `caseStudyEn` or `caseStudyEs` that differ from the published value, refuse `--apply`. Or carry those keys forward into a new draft instead of nulling it.

### WR-07: `readHeadline` silently truncates a headline that spans more than one `>` line

**File:** `src/features/site-settings/copy-doc.ts:72-81`
**Issue:** `grab` returns the first non-empty indented quote line. If the headline in `docs/copy.md` is wrapped onto two `  >` lines, only the first half is loaded and published, with no error. `grabQuote` (About/Now) joins continuation lines, so the two readers behave differently.
**Fix:** Collect consecutive `^\s+>` lines, then `join(" ").trim()`. Throw if the result is empty.

### IN-02: Retire cascades into experiences the loader claims never to touch, and orphans Blob media

**File:** `scripts/load-content.ts:12-14, 249-263`
**Issue:** Deleting a project cascades `experience_projects`, including links from unmanaged experiences such as Sofka, which contradicts the header comment. Blob objects referenced by `media` and `coverImage` stay behind.
**Fix:** Print the cascaded relation rows and blob URLs in the dry-run. Fix the header comment.

### IN-03: Unknown flags are ignored silently

**File:** `src/lib/content-load/target.ts:22-50`
**Issue:** `--apply=true`, `--dry-run`, and typos are all accepted and ignored. This fails safe (dry-run), but it is confusing: `--apply=true` prints "dry-run".
**Fix:** Reject any argument that is not `--target=`, `--only=`, `--apply` or `--allow-production`.

### IN-04: No duplicate validation in `positioning.ts`

**File:** `scripts/content/positioning.ts`, `scripts/load-content.ts:355-359, 457-468`
**Issue:** A repeated skill name in `skills`, `skillNames` or `projectSlugs` is only caught by a database constraint at apply time (after earlier groups have committed, see WR-02). `sameSet` also counts duplicates.
**Fix:** Add a unit test or a planning-time check that all lists are unique.

### IN-05: Project placements without a `docs/content` file are ignored silently

**File:** `scripts/load-content.ts:340-353`
**Issue:** The loop goes over content files, so a placement with no file (for example after a slug rename) produces no line at all.
**Fix:** After the loop, print a line for each `positioning.projects` slug that was not seen.

### IN-06: Lint walks Tiptap JSON structure and hrefs

**File:** `scripts/load-content.ts:384-387`, `scripts/check-phase-4-1.ts:234-246`
**Issue:** `lintStrings` and `lintPair` over `caseStudyEn/Es` include node type names and link `href`s. A case-study link to a `*.vercel.app` URL or a URL with digits trips `infra` or `parity`, even though the lint header says URLs are the caller's responsibility.
**Fix:** Extract only `text` nodes from rich-text docs before linting.

### IN-07: `nowOk` is declared twice with different meanings

**File:** `scripts/check-phase-4-1.ts:141, 347`
**Issue:** The block-scoped `nowOk` in the settings branch shadows the later function-scoped `nowOk`. The behaviour is correct, but the shadowing is a trap for edits.
**Fix:** Rename the first one to `nowMentionsPrendo`.
