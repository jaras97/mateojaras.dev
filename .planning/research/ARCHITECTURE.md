# Architecture Research

**Domain:** Bilingual portfolio (en at `/`, es at `/es`) + single-admin CMS on Next.js 16.4 App Router with Cache Components
**Researched:** 2026-10-29
**Confidence:** MEDIUM overall (HIGH where it comes straight from the Next 16.4.3 docs shipped in `node_modules/next/dist/docs`; MEDIUM for next-intl / Better Auth / Blob via Context7; LOW for react-pdf-on-Vercel specifics)

## Standard Architecture

### System Overview

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ EDGE: src/proxy.ts                                                           │
│   /admin/*  -> session-cookie presence check (getSessionCookie) -> next()    │
│   everything else (no dot, not /api) -> next-intl middleware                 │
│       /about -> rewrite /en/about   /es/sobre-mi -> rewrite /es/about        │
│       /en/about -> redirect /about  (as-needed prefix, detection off)        │
├──────────────────────────────────────────────────────────────────────────────┤
│ APP ROUTER (two root layouts, both prerendered shells)                       │
│                                                                              │
│  app/[locale]/layout.tsx  (root #1)        app/admin/layout.tsx (root #2)    │
│   ├ (site)/ pages: /, projects/[slug],       ├ login/                         │

│ FEATURE LAYER  src/features/<entity>/                                        │

│   admin-queries.ts (uncached, drafts)  actions.ts ('use server')             │
│   validation.ts (Zod)  components/ (forms, tables, public sections)          │
│                                                                              │
│ SHARED  src/lib/{auth,db,cache-tags,i18n-fields,export-content,env}.ts       │

```

The mental model: **the public site is a static shell per URL, regenerated by tags**. Every public read is a `'use cache'` function tagged by entity. The admin never reads through those functions. Every admin write is a Server Action that ends with `updateTag(...)` and a deferred `exportContent(...)`. On Vercel the in-memory runtime cache does not survive between invocations (Next docs, `use cache` > Runtime caching considerations), so the architecture must make every public route fully prerenderable; the DB is then hit only during build and on tag revalidation, never per visitor.

### Component Responsibilities

| Component | Responsibility | Typical Implementation |
|-----------|----------------|------------------------|
| `src/proxy.ts` | Locale rewrite/redirect for the site tree; optimistic cookie check for `/admin`. Nothing else. | `createMiddleware(routing)` from `next-intl/middleware` + `getSessionCookie` from `better-auth/cookies`; one matcher excluding `api`, `_next`, `_vercel`, dotted files |

### Structure Rationale

- **`app/[locale]` as root layout:** makes `locale` a *root param*, which is the only way a `'use cache'` scope can learn the locale without `headers()` (Next docs: root params read inside a cached function become part of its key; `headers()`/`cookies()` throw). The internal file paths stay English (`about`, `projects`); next-intl's `pathnames` map produces `/es/sobre-mi` and `/es/proyectos/[slug]` by rewriting in the proxy. No duplicated page files per language.
- **`app/admin` as a second root layout:** keeps `/admin` out of the locale tree so `/admin` is never rewritten to `/en/admin`, carries no hreflang, and can use a fixed UI locale. Next supports multiple root layouts; the only side effect is that `locale()` is typed `string | undefined` and returns `undefined` under `/admin`, which is correct.
- **Route handlers under `/api` + rewrites:** `next/root-params` is not available in Route Handlers (Next docs, Restrictions), so handlers take `lang` from their own `[lang]` segment. `/api` is already excluded from the intl matcher, and `rewrites()` give the pretty public URLs (`/resume.json`, `/resume.es.json`, `/cv/en.pdf`, `/cv/es.pdf`). The proxy runs before rewrites but skips dotted paths, so those URLs never touch next-intl.
- **`queries.ts` vs `admin-queries.ts`:** a hard file boundary stops a draft read from ever landing in a cached function. Do not use file-level `'use cache'`.
- **Locale-agnostic queries:** rows carry both `_en` and `_es`; `localized()` picks at render time. One DB read, one cache entry per entity, both locales served; tags need no locale suffix; the same function works from Route Handlers (which pass `lang` themselves).

## Architectural Patterns

### Pattern 1: One proxy, two jobs

**What:** `src/proxy.ts` branches on pathname: `/admin/*` gets an optimistic cookie check, everything else goes to next-intl's middleware. Real auth never happens here.
**When to use:** always; this is the only proxy the app has.
**Trade-offs:** CLAUDE.md says "proxy.ts only checks the session cookie"; it must *also* host the intl rewrite, otherwise `/es/sobre-mi` cannot map to `app/[locale]/(site)/about`. Flag this as a one-line amendment to CLAUDE.md. `localeDetection: false` keeps `/` always English (SEO-stable, no cookie-driven redirects to `/es`); the language switch is an explicit link.

```ts
// src/proxy.ts
import createIntlMiddleware from 'next-intl/middleware'
import { getSessionCookie } from 'better-auth/cookies'
import { NextResponse, type NextRequest } from 'next/server'
import { routing } from '@/i18n/routing'

const intl = createIntlMiddleware(routing)

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl
  if (pathname.startsWith('/admin')) {
    if (pathname === '/admin/login' || getSessionCookie(request)) return NextResponse.next()
    return NextResponse.redirect(new URL('/admin/login', request.url))
  }
  return intl(request)
}

export const config = { matcher: ['/((?!api|_next|_vercel|.*\\..*).*)'] }
```

```ts
// src/i18n/routing.ts
export const routing = defineRouting({
  locales: ['en', 'es'],
  defaultLocale: 'en',
  localePrefix: 'as-needed',
  localeDetection: false,
  pathnames: {
    '/': '/',
    '/projects/[slug]': { en: '/projects/[slug]', es: '/proyectos/[slug]' },
    '/about': { en: '/about', es: '/sobre-mi' },
    '/now': { en: '/now', es: '/ahora' },          // es slug not in PROJECT.md; confirm with Teo
    '/contact': { en: '/contact', es: '/contacto' },
  },
})
```

```ts
// src/i18n/request.ts  (next-intl 4.14 recommended shape)
export default getRequestConfig(async ({ locale }) => {
  if (!locale) {                                   // no override: read the root param
    const value = await rootParams.locale()
    if (!hasLocale(routing.locales, value)) notFound()
    locale = value
  }
  return { locale, messages: (await import(`../../messages/${locale}.json`)).default }
})
```

Server Actions and Route Handlers cannot read root params, so they pass the locale explicitly: the contact form posts a hidden `locale` field and the action calls `getTranslations({ locale, namespace: 'Contact' })`.

### Pattern 2: Entity tags, locale in the key

**What:** tags name *what changed*, never *which language*. The cache key already differs per locale (via the root param or the `lang` argument), and `updateTag('projects')` expires every entry carrying that tag, in both locales, in pages and in handlers.
**When to use:** every `'use cache'` function in `queries.ts` and every `generateMetadata` that reads the DB.
**Trade-offs:** `settings` is read by the site layout (status line, footer, metadata), so saving settings invalidates every public page. For a portfolio with ~10 pages this is the right trade; do not split `settings` into sub-tags in v1.

```ts
// src/lib/cache-tags.ts
export const tags = {
  settings: 'settings',
  projects: 'projects',                    // list, home, sitemap, resume
  project: (slug: string) => `project:${slug}`,
  experience: 'experience',
  skills: 'skills',
  education: 'education',
  resume: 'resume',                        // resume_versions.overrides
} as const
```

| Cached function (`queries.ts`) | Tags | Consumed by |
|---|---|---|
| `getSettings()` | `settings` | `(site)/layout`, every `generateMetadata`, `/now`, resume |
| `getPublishedProjects()` | `projects` | home, `sitemap.ts`, prev/next on case study |
| `getPublishedSlugs()` | `projects` | `generateStaticParams`, sitemap |
| `getProject(slug)` | `project:${slug}`, `projects` | `projects/[slug]/page` + its metadata |
| `getExperiences()` | `experience`, `skills` (joined) | about, resume |
| `getSkills()` | `skills` | about, home, project pages (via join) |
| `getEducation()` | `education` | about, resume |
| `getResumeData()` | `resume`, `settings`, `experience`, `skills`, `education`, `projects` (explicit, one `cacheTag(...)` call) | `/api/cv/[lang]`, `/api/resume/[lang]` |

| Server Action | `updateTag(...)` calls |
|---|---|
| `saveSettings` | `settings` |
| `saveProject` / `publishProject` / `reorderProjects` / `deleteProject` | `projects`, `project:${slug}` (plus the old slug if it changed; slugs are immutable once published, so this is a draft-only case) |
| `saveExperience` / reorder | `experience` |
| `saveSkill` / reorder (also changes labels inside projects and experiences) | `skills`, `projects`, `experience` |
| `saveEducation` | `education` |
| `saveResumeOverrides` / `snapshotCv` | `resume` |

Explicitly tag composite queries rather than relying on tag propagation from nested cached calls; the Next docs guarantee multiple tags per call (up to 128) but say nothing about inheritance.

### Pattern 3: Prerendered case studies, App Shell for new slugs

**What:** `projects/[slug]/page.tsx` exports `generateStaticParams` returning every published slug (combined with the `[locale]` params this yields 2 x N pages). The page awaits `params` *inside* a `<Suspense>` so an unlisted slug (published after the last deploy) is served as an App Shell and upgraded in the background; `notFound()` handles unknown or unpublished slugs.
**When to use:** the project route and, by the same token, any future `[slug]` route.
**Trade-offs:** With Cache Components `generateStaticParams` **must return at least one param** and `dynamicParams` is unsupported (Next docs, Migrating guide). The build therefore needs a database with at least one published project; the phase 2 seed must guarantee that, and Vercel builds must have `DATABASE_URL` (preview -> `dev` branch, production -> `main`).

```tsx
// app/[locale]/(site)/projects/[slug]/page.tsx
export async function generateStaticParams() {
  return (await getPublishedSlugs()).map((slug) => ({ slug }))
}

export async function generateMetadata({ params }: PageProps<'/[locale]/projects/[slug]'>) {
  const { slug } = await params
  return projectMetadata(slug)              // 'use cache' inside; reads locale() + getSettings()
}

export default function Page({ params }: PageProps<'/[locale]/projects/[slug]'>) {
  return (
    <Suspense fallback={<CaseStudySkeleton />}>
      <CaseStudy params={params} />
    </Suspense>
  )
}

async function CaseStudy({ params }: Pick<PageProps<'/[locale]/projects/[slug]'>, 'params'>) {
  const [{ slug }, loc] = await Promise.all([params, locale()])
  const project = await getProject(slug)
  if (!project) notFound()
  return <Article title={localized(project, 'title', loc)} … />
}
```

`<Link prefetch={true}>` on project cards so navigation to an unlisted slug starts the upgrade before the click (Next docs, ISR with Cache Components).

### Pattern 4: Session behind Suspense in the admin

**What:** the admin root layout renders its static chrome, then `<Suspense fallback={<AdminSkeleton />}><AuthGate>{children}</AuthGate></Suspense>`. `AuthGate` is the only place the layout reads `headers()`; children are returned only after the session resolves, so nothing below renders for an anonymous request. Every Server Action repeats `requireSession()` first.
**When to use:** all of `/admin` except `/admin/login`.
**Trade-offs:** Under Cache Components a request-time read outside a boundary is flagged by validation (Next docs, Authentication with Cache Components). Pushing it into a boundary keeps the build green and the sidebar instant. Admin pages read uncached `admin-queries.ts` and must themselves sit under `loading.tsx` or a `<Suspense>`.

```ts
// src/lib/session.ts
import 'server-only'
export async function requireSession() {
  const session = await auth.api.getSession({ headers: await headers() })
  if (!session) redirect('/admin/login')
  return session
}
```

Better Auth config: `emailAndPassword: { enabled: true, disableSignUp: true }`, Drizzle adapter, one user inserted by `scripts/seed.ts` from env (`ADMIN_EMAIL`, `ADMIN_PASSWORD` used once, never committed).

### Pattern 5: PDF and JSON Resume as thin handlers over one cached DTO

**What:** `getResumeData()` returns a plain, serializable DTO (settings, experiences with skills, skills, education, featured projects, latest `resume_versions.overrides` per locale). `toJsonResume(data, lang)` and `renderCv(data, lang)` are pure. Handlers validate `lang` with `hasLocale`, call those, and set headers. Both export `generateStaticParams` -> `en`, `es`, so with no runtime API access they prerender at build and regenerate on `updateTag` (Next docs: GET handlers follow the same model as pages under Cache Components; `'use cache'` goes on a helper, not on `GET`).
**When to use:** phase 3 (the PDF-with-accents gate).
**Trade-offs:** Rendering a PDF during `next build` means the fonts must be traceable at build and at request time. If build-time rendering misbehaves, `await connection()` at the top of `GET` makes the handler per-request while data stays cached (a ~100-300 ms render; traffic is tiny). Verify at the phase 3 gate: publish -> fetch `/cv/en.pdf` -> content updated.

```ts
// app/api/cv/[lang]/route.ts
export function generateStaticParams() { return routing.locales.map((lang) => ({ lang })) }

export async function GET(_: Request, { params }: RouteContext<'/api/cv/[lang]'>) {
  const { lang } = await params
  if (!hasLocale(routing.locales, lang)) return new Response('Not found', { status: 404 })
  const data = await getResumeData()                       // 'use cache' + tags
  const pdf = await renderCv(data, lang)                   // renderToBuffer(<CvDocument/>)
  return new Response(pdf, {
    headers: {
      'Content-Type': 'application/pdf',
      'Content-Disposition': `inline; filename="mateo-jaramillo-cv-${lang}.pdf"`,
    },
  })
}
```

```ts
// next.config.ts additions
rewrites: async () => [
  { source: '/resume.json',    destination: '/api/resume/en' },
  { source: '/resume.es.json', destination: '/api/resume/es' },
  { source: '/cv/:lang(en|es).pdf', destination: '/api/cv/:lang' },
],
serverExternalPackages: ['@react-pdf/renderer'],          // already in Next's auto list; explicit is harmless
outputFileTracingIncludes: { '/api/cv/[lang]': ['./assets/fonts-pdf/**/*'] },
```

Fonts: static TTF instances per weight (Hanken Grotesk Regular/Medium/SemiBold, Funnel Display SemiBold, Geist Mono Regular) registered once in `features/resume/pdf/fonts.ts` with `path.join(process.cwd(), 'assets/fonts-pdf', file)`; `Font.registerHyphenationCallback((w) => [w])` to stop react-pdf splitting Spanish words. Tildes and ñ are a font-coverage issue, not a renderer issue: these families cover Latin Extended.

Admin side: `snapshotCv` action renders both languages, `put()`s them to Blob (`cv/<version>/cv-<lang>.pdf`, well under the 4.5 MB server-upload cap), inserts `resume_versions`, then `updateTag('resume')`. The public URL renders live from cached data (always in sync with the site); the Blob copy is history and a fallback. Decision for Teo: if he prefers the public link to serve *exactly* the reviewed snapshot, the handler becomes a redirect to the latest `pdfUrl` instead.

### Pattern 6: Client uploads to Blob, URL stored by the normal save action

**What:** the admin `ImageField` (client) calls `upload()` from `@vercel/blob/client` with `handleUploadUrl: '/api/blob/upload'`. The handler's `onBeforeGenerateToken` verifies the session (`auth.api.getSession({ headers: request.headers })`) and returns constraints. The returned `blob.url` is written into the React Hook Form field (`coverImage`, `media[]` with `altEn`/`altEs`); nothing is persisted until the entity's Server Action runs (`saveProject`), which validates the URL host with Zod.
**When to use:** all media. Server-side `put()` is reserved for files the server itself produces (CV snapshots, JSON backups).
**Trade-offs:** Client upload avoids the 4.5 MB Vercel request-body cap (short MP4 demos) and keeps function time near zero. Do not depend on `onUploadCompleted`: it needs a public callback URL and does not fire on localhost. Orphaned blobs (uploaded, never saved) are tolerable in v1; a `list()`-diff cleanup script is backlog.

```ts
// app/api/blob/upload/route.ts
export async function POST(request: Request) {
  if (!process.env.BLOB_READ_WRITE_TOKEN) return Response.json({ error: 'Blob not configured' }, { status: 503 })
  const body = (await request.json()) as HandleUploadBody
  const result = await handleUpload({
    body, request,
    onBeforeGenerateToken: async (pathname, clientPayload) => {
      const session = await auth.api.getSession({ headers: request.headers })
      if (!session) throw new Error('Unauthorized')
      const { entity, id } = JSON.parse(clientPayload ?? '{}')
      if (!pathname.startsWith(`${entity}/${id}/`)) throw new Error('Bad path')
      return {
        allowedContentTypes: ['image/png', 'image/jpeg', 'image/webp', 'image/avif', 'video/mp4', 'video/webm'],
        maximumSizeInBytes: 25 * 1024 * 1024,
        addRandomSuffix: true,
      }
    },
  })
  return Response.json(result)
}
```

`next.config.images.remotePatterns` must allow `*.public.blob.vercel-storage.com`; public pages render media with `next/image` and the locale-appropriate alt.

### Pattern 7: Export after the response, not before

**What:** every write action ends with `after(() => exportContent('projects'))`. `exportContent(table)` selects all rows (drafts included; auth tables and `contact_messages` excluded), serializes with stable key order and ISO dates, and writes to `content/<table>.json` locally or `backup/<YYYY-MM-DD>/<table>.json` in Blob (`access: 'private'`, `allowOverwrite: true`) when `process.env.VERCEL` is set. `scripts/export-content.ts` (`pnpm export:content`) and `scripts/seed.ts --from-content` reuse the same module.
**When to use:** every action in `actions.ts`; the lib is built in phase 2 so the seed round-trip can be tested before the admin exists.
**Trade-offs:** `after()` does not delay the admin's response and runs even if the action redirects (Next docs, `after`). Until `BLOB_READ_WRITE_TOKEN` exists (phase 3) the production branch logs a clear warning and skips; it never fakes a write. `content/` is outside `src/` and imported by nothing, so writing it in dev does not trigger Turbopack rebuilds.

### Pattern 8: Motion islands wrap server-rendered children

**What:** `src/components/motion/` holds the only `'use client'` files that import `gsap`/`@gsap/react`/`motion/react`: `Reveal` (staggered mount reveal), `SplitHeading` (GSAP SplitText), `ScrubScene` (ScrollTrigger scrub, `useGSAP` with a scoped ref), `ThemeToggle` (View Transitions), `LocalClock` (client-side time for the status line), `MotionProvider` (`<MotionConfig reducedMotion="user">`). Each accepts `children` that were rendered on the server, so the static shell contains the full HTML and the islands only attach behaviour after hydration.
**When to use:** phase 4. Everything outside `components/motion` is motion-free.
**Trade-offs:** Islands must not read `useSearchParams` (always needs Suspense) nor `usePathname` in the shared header (it suspends while the `[slug]` shell is generated; if an active-link indicator is needed, isolate it in a tiny Suspense-wrapped leaf). Initial hidden states for reveals must be applied by JS after mount (or by a class the pre-paint script adds only when JS and `no-preference` are present), never by default CSS, so bots, no-JS users and the LCP element see content; keep the hero's LCP text reveal under ~400 ms and never hide the hero image. Theme comes from `localStorage` + `matchMedia` in an inline pre-paint script (`suppressHydrationWarning` on `<html>`); do not read a theme cookie on the server, it would punch a dynamic hole in every shell.

## Data Flow

### Public request (visitor)

```
GET /es/proyectos/manuj
  -> proxy: intl rewrite -> /es/projects/manuj (no auth, no DB)
  -> prerendered shell for (locale=es, slug=manuj) if listed at build
       else App Shell (/[locale]/projects/[slug]) + background upgrade, cached after
  -> HTML includes server-rendered article, Marginalia, media; islands hydrate
  -> zero DB queries at request time when everything is tagged and cached
```

### Admin publish (read-your-writes + both locales)

```
Admin form (RHF + Zod client) --submit--> saveProject(formData)   [Server Action]
  1. requireSession()                      (auth.api.getSession, headers())
  2. projectSchema.parse(...)              (Zod, server)
  3. drizzle update/insert                 (Neon)
  4. updateTag('projects'); updateTag(`project:${slug}`)
  5. after(() => exportContent('projects'))
  6. redirect('/admin/projects/<id>')      -> admin reads admin-queries (uncached), sees the draft
Next request to /projects/manuj or /es/proyectos/manuj regenerates from getProject(slug);
home (both locales), sitemap and /cv/*.pdf regenerate on their next hit via the shared tags.
```

### Media upload

```
ImageField (client) -> POST /api/blob/upload {generate-client-token, pathname, clientPayload}
  -> handler verifies session, returns token (type/size constraints)
ImageField -> PUT blob storage directly -> { url }
ImageField -> setValue('coverImage', url)  -> later saveProject() persists it -> updateTag
```

### CV / JSON Resume

```
GET /cv/es.pdf -> rewrite -> /api/cv/es -> getResumeData() [cached, 6 tags]
  -> renderCv(data, 'es') -> application/pdf
GET /resume.json -> rewrite -> /api/resume/en -> getResumeData() -> toJsonResume(data, 'en')
Admin "Snapshot CV" -> renderCv x2 -> put() to Blob -> insert resume_versions -> updateTag('resume')
```

### Contact

```
ContactForm (client, hidden locale + honeypot) -> sendMessage(formData) [Server Action]
  -> Zod -> honeypot check -> Upstash ratelimit by ip hash -> insert contact_messages
  -> Resend email (templated with getTranslations({ locale })) -> return state
No cache involvement; page shell stays static because the form is a client island with a Server Action.
```

### State Management

No client state library. Server state lives in Postgres and reaches the UI through RSC. Admin forms hold local state in React Hook Form; TanStack Table and dnd-kit hold ephemeral UI state; order changes commit through a Server Action (`reorderProjects(ids)`) and the page refreshes from `admin-queries`. Theme lives in `localStorage`. The language is the URL.

### Key Data Flows

1. **Content authority:** Postgres is the single source; `content/*.json` is a derived, committed backup; `docs/content/` is Teo's human-authored input used once by the seed.
2. **Localization split:** data rows carry `_en/_es`; UI strings live in `messages/*.json`; the locale enters only at render time (`locale()` root param) or as an explicit argument (actions, handlers).
3. **Invalidation:** actions -> `updateTag` (immediate, read-your-writes) -> prerendered pages/handlers regenerate lazily. `revalidateTag(tag, 'max')` is reserved for any future webhook; not needed in v1.

## Scaling Considerations

| Scale | Architecture Adjustments |
|-------|--------------------------|
| 0-1k visitors/day (v1 reality) | Everything prerendered; Neon is touched by builds, revalidations, the admin and the contact form only. Nothing to tune. |
| Spike (a post goes viral) | Still static at the CDN. The only per-request work is the contact action (rate limited) and PDF renders if `connection()` was added; if so, move the PDF to the Blob snapshot redirect. |
| 100k+ | Not a target. If it ever mattered: `'use cache: remote'` for shared runtime cache, image CDN already handled by `next/image` + Blob. |

### Scaling Priorities

1. **First thing that breaks:** a dynamic hole in a public page (a stray `headers()`, `Date.now()` or uncached query) turns a static route into a per-visitor Neon query with cold starts. Prevention: the dev overlay validation under Cache Components, plus a Playwright check that `x-vercel-cache`/`x-nextjs-cache` headers show prerendered responses on the four routes in both locales.
2. **Second:** PDF render cost if the handler is made dynamic. Fix: serve the Blob snapshot.

## Anti-Patterns

### Anti-Pattern 1: Reading the request inside a cached scope
**What people do:** call `headers()`, `cookies()`, next-intl's legacy `requestLocale`, or `auth.api.getSession()` inside a `'use cache'` function or a component it renders.
**Why it's wrong:** throws `next-request-in-use-cache`; on a dynamic route it can pass `next build` and fail at runtime.
**Do this instead:** read the locale from `next/root-params`; read session/headers in uncached admin code behind Suspense; pass values in as arguments.

### Anti-Pattern 2: Server-side timestamps in the status line
**What people do:** compute "it is 14:32 in Medellín, 2 h overlap with Toronto" during render.
**Why it's wrong:** `Date.now()` during prerender is treated as runtime data by Cache Components (docs: "Random values and timestamps"), making the hero dynamic on every page.
**Do this instead:** the server renders availability, city and the UTC-5 label from `settings`; `LocalClock` (client island) fills the live time and overlap after mount, rendering a neutral placeholder first.

### Anti-Pattern 3: Locale-suffixed tags
**What people do:** `cacheTag('projects:es')` and `updateTag` both suffixes in every action.
**Why it's wrong:** doubles the invalidation surface and invites forgetting one language. The cache key already distinguishes locales.
**Do this instead:** entity tags only (Pattern 2).

### Anti-Pattern 4: Awaiting `params` at the top of a layout or page under `[slug]`
**What people do:** `const { slug } = await params` in the page body or in `(site)/layout.tsx`.
**Why it's wrong:** ties the App Shell to one URL; unlisted slugs then block on a full server render and the shared layout stops being reusable.
**Do this instead:** pass the `params` promise into a Suspense-wrapped child (Pattern 3). Only `[locale]` is awaited at layout level, and it is a root param with known values.

### Anti-Pattern 5: Returning `[]` from `generateStaticParams` or exporting `dynamicParams`
**What people do:** "defer everything to runtime" habits from Next 14/15.
**Why it's wrong:** both fail the build under Cache Components.
**Do this instead:** return real published slugs; `notFound()` for anything else.

### Anti-Pattern 6: Admin inside `[locale]`
**What people do:** `app/[locale]/admin/...` to reuse the layout.
**Why it's wrong:** `/admin` gets hreflang, locale rewrites and a `generateStaticParams` it does not need; `/es/admin` becomes a second entry point; the public chrome (status line, footer) leaks into the CMS.
**Do this instead:** a second root layout at `app/admin` (Pattern 4).

### Anti-Pattern 7: Wrapping pages in client components for motion
**What people do:** `'use client'` on a page or section so GSAP can reach the DOM.
**Why it's wrong:** content becomes props serialized into the RSC payload, Server Component data access is lost, and the whole subtree ships as JS.
**Do this instead:** server-render the content, wrap it in a motion island that takes `children` (Pattern 8).

### Anti-Pattern 8: Server `put()` for media uploads from a Server Action
**What people do:** `formData.get('file')` -> `put()`.
**Why it's wrong:** 4.5 MB request cap on Vercel, double transfer, slow actions.
**Do this instead:** client upload with a session-gated token route (Pattern 6).

### Internal Boundaries

| Boundary | Communication | Notes |
|----------|---------------|-------|
| `app/*` <-> `features/*` | Pages import `queries.ts`/`components`; admin pages import `admin-queries.ts`/forms; forms import `actions.ts` | Pages never import Drizzle directly. |
| `queries.ts` <-> `admin-queries.ts` | None | Separate files so `'use cache'` never touches drafts. |
| `actions.ts` -> `lib/cache-tags.ts`, `lib/export-content.ts` | Direct calls | Every action ends with `updateTag` + `after(exportContent)`. |

**Things that do not fit the phase labels cleanly (flag for the roadmap):**

1. The public route tree and the cache/i18n integration must exist in **phase 2**, not phase 4, because the day-3 Plan B decision (`cacheComponents: false` + ISR) can only be made against a running `[locale]` + `'use cache'` + `next/root-params` skeleton.
2. `export-content` is a phase 2 library (seed round trip) that is only *wired into actions* in phase 3.
3. `/resume.json` and `/cv/*.pdf` are public URLs but belong to phase 3 because the PDF gate lives there; phase 4 only links to them.
4. Hero variants in phase 1 precede the schema; they must be built against a props contract, not against the DB, or phase 1 will quietly pull phase 2 forward.
5. Blob (phase 3) is needed by production `exportContent` too; between the phase 2 deploy and the Blob token, production exports are skipped with a warning. Acceptable, but say so in `docs/decisions.md`.
6. CLAUDE.md's "proxy.ts only checks the session cookie" needs the amendment "and runs the next-intl rewrite for the site tree".
